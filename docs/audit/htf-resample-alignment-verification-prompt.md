2026-09-12 по итогам `docs/audit/recommendations-post-harmonic-audit.md`.

поэтому `npm run ci`/`npm run build`/`npm run test`/`npm run lint` на

"Чек-лист", подтвердите или опровергните со ссылкой на файл/строку, и

## 3. Точки, где я сам не уверен на 100% — прошу отдельно перепроверить и отполировать

### 3.1. Хрупкость magic numbers в аудит-скрипте и новых тестах стабильности

`backtest/htf-resample-stability-audit.ts`, `order-block-strategies.test.ts`,
`fvg-strategies.test.ts` — во всех трёх используется одна и та же
константа `STABLE_HORIZON_TIME = Date.UTC(2025,0,1)/1000 + 11400`
(≈ индекс 190 сырых баров), подобранная ВРУЧНУЮ под конкретные
`buildRealisticSeries(1200, 42)` (сид 42, 1200 баров, конкретная формула
импульсов/шума) и `WINDOW_SIZE=500`. Смысл этой границы — "достаточно
далеко от края скользящего окна, чтобы не попасть на зону, чей
`broken`-статус ещё может законно пересчитаться по мере роста окна
обзора" (это НЕ баг, см. диагноз в changelog, раздел про "легитимное
наблюдение").

**Риск:** если кто-то поменяет `WINDOW_SIZE`, сид, формулу генератора
или число сдвигов в БУДУЩЕМ, эта константа может перестать быть
"достаточно далеко" и тест начнёт ложно падать (или, хуже, ложно
проходить, случайно не захватив ни одной зоны — я в коде добавил
`expect([...snapshots][0]).not.toBe('')`, но эта защита слабая: она
ловит "вообще ноль зон", а не "недостаточно зон для содержательной
проверки").

**Что сделать:** либо (а) явно задокументировать это одним комментарием
"если меняете WINDOW_SIZE/сид/генератор — пересчитайте эту константу
через `backtest/htf-resample-stability-audit.ts` вручную" (частично уже
сделано, но проверьте формулировку и добавьте, если её нет в одном из
трёх мест), либо (б), если есть время — переписать проверку так, чтобы
она сама находила "устоявшуюся" границу программно (например: искать
самую МОЛОДУЮ зону, чей статус не менялся на протяжении последних 10 из
25 сдвигов, и требовать стабильности только для зон старше неё), что
устранило бы хрупкость полностью. Вариант (б) предпочтительнее, если
не жалко времени — это именно то "отполировать", о чём просит пользователь.

### 3.2. Дублирование `buildRealisticSeries`/`mulberry32` в трёх файлах

Один и тот же генератор синтетических данных (ГПСЧ mulberry32 +
формула импульсов) буквально скопирован в `backtest/htf-resample-
stability-audit.ts`, `order-block-strategies.test.ts` и
`fvg-strategies.test.ts`. Я сделал это НАМЕРЕННО, по образцу уже
принятой в проекте конвенции (каждый `*.test.ts`-файл в
`src/compute/patterns/` содержит свои локальные `candle`/`ramp`/`flat`-
хелперы, а не импортирует общий `test-utils` — общего файла для этого в
проекте нет). Но три копии ОДНОГО И ТОГО ЖЕ генератора (не просто
похожих хелперов, а идентичного кода) — это уже граница, где
дублирование может быть неоправданным.

**Что сделать:** решите, стоит ли:
- оставить как есть (соответствует духу существующей конвенции проекта
  — каждый тестовый файл самодостаточен, не тянет общие импорты между
  тестами разных модулей), ЛИБО
- вынести `buildRealisticSeries`/`mulberry32` в отдельный файл (например
  `backtest/synthetic/realistic-series.ts`, по аналогии с уже
  существующим `backtest/synthetic/harmonic-data.ts`) и импортировать во
  всех трёх местах — снижает риск, что копии разъедутся при будущих
  правках одной из них незаметно для остальных двух.

Если выберете второй вариант — после рефакторинга ОБЯЗАТЕЛЬНО заново
прогнать `npm run backtest:htf-resample-audit` и оба новых теста, чтобы
убедиться, что вынос не изменил детерминированный результат ГПСЧ (сид
42 должен давать те же самые числа).

### 3.3. Экспорт `detectHtfObZones`/`detectHtfFvgZones` — не расширяет ли это публичный API случайно

Обе функции раньше были `function foo(...)` (module-private), стали

**Проверить:** не попадают ли эти два новых экспорта случайно в какой-то
публичный barrel-файл (`src/compute/patterns/index.ts` или похожий),

по назначению (например, если там есть `export * from './order-block-
nested'`). Если попадают — либо это не страшно (внутренний модуль
приложения, не npm-пакет с семантическим версионированием), либо, если
хочется быть аккуратнее, переименовать в тестах импорт с явным
комментарием "test-only export" рядом с определением функции (я уже
добавил такой комментарий у обеих — проверьте, что он не потерялся при
последующих правках).

### 3.4. Рекомендация 4 — решение НЕ трогать `overlapTop <= overlapBottom`

В changelog зафиксировано решение не добавлять эпсилон в
`order-block-nested.ts`/`fvg-nested.ts` (строка `if (overlapTop <=
overlapBottom) continue;`), в отличие от уже существующего `PRZ_EPS` в
`harmonic-pattern.ts`. Обоснование: там обе зоны (HTF и M1) имеют
реальную ненулевую ширину по построению, в отличие от математически
вырожденного PRZ ab-cd.

**Перепроверить свежим взглядом:** согласны ли вы с этим обоснованием
после реального прогона `npm run backtest:htf-resample-audit` и
`npm run test`? Если в процессе полноценного прогона (с реальными
данными, не синтетикой) обнаружите случаи, когда `overlapTop ===
overlapBottom` (или отличается на пренебрежимо малую величину из-за
округления HTF-группировки) реально случается и ошибочно даёт "нет
перекрытия" — добавьте эпсилон по аналогии с `PRZ_EPS`, той же
относительной величины (~0.1–0.2% от цены), и задокументируйте это как
дополнение к Рекомендации 4 в `CHANGES_APPLIED_HTF_RESAMPLE_ALIGNMENT_20260912.md`
(допишите новую секцию, не переписывайте уже написанное).

### 3.5. `alignToAbsoluteHtfBoundary` — граничный случай "не найдено кратной свечи"

Функция (перенесена из `zigzag.ts` в `fvg-strategies-shared.ts` без
изменения логики) молча возвращает исходный массив НЕ ИЗМЕНЁННЫМ, если
ни одна из первых `factor` свечей не имеет `time % groupSeconds === 0`
(см. комментарий в коде). Это осознанно (не терять больше `factor-1`
свечей и не обвалиться в пустой результат), но означает, что для
данных с "нестандартным" эпохальным сдвигом (не выровненных на минуту от
UNIX-эпохи — например, если источник котировок отдаёт время с произвольным
смещением) выравнивание молча НЕ СРАБОТАЕТ, и баг из Рекомендации 1
вернётся незаметно.

**Проверить:** для каждого реального источника данных в проекте
(`src/data/*` — Binance, Deriv, Yahoo, Finnhub, TwelveData) убедиться,
что отдаваемые ими `time` в `Candle` — это секунды UNIX-эпохи,
выровненные на границу минуты (т.е. `time % 60 === 0` для M1). Если
хотя бы один источник этого не гарантирует — добавить туда нормализацию
времени при парсинге ответа API, либо явно задокументировать
ограничение в комментарии у `alignToAbsoluteHtfBoundary`.
