# Протокол форвард-теста против переобучения через сам процесс аудита

## Проблема

Каждая ручная правка (`docs/changelog/CHANGES_APPLIED_*`), сделанная на
основе исторических демо-данных или `npm run backtest` на уже скачанном
файле свечей, немного подгоняет систему под ЭТИ КОНКРЕТНЫЕ данные. Чем
больше отдельных параметров (пороги, множители, веса паттернов) подкручено
вручную по одному и тому же историческому набору сделок, тем выше риск, что
наблюдаемое улучшение — статистический артефакт конкретной выборки
(проблема множественного тестирования / researcher degrees of freedom), а
не реальный edge, который сохранится на новых данных.

У `backtest/` уже был `inSampleRatio` — разбиение одного статического файла
свечей на in-sample/out-of-sample. Это разбиение полезно для тюнинга
гиперпараметров конкретного прогона, но **не защищает от главного риска**:
`npm run backtest` можно перезапускать сколько угодно раз с разными
параметрами против одного и того же исторического файла, неявно подгоняя
решение под "out-of-sample" часть тоже — после десятков попыток эта часть
перестаёт быть по-настоящему невиданной.

## Решение — wall-clock forward-test

Единственная надёжная защита — оценивать правку на данных, время входа
которых **физически позже момента, когда правка была заморожена**. Такие
данные не могли быть видны/использованы при разработке правки, сколько бы
раз бэктест ни перезапускали на старых файлах.

Реализовано в `backtest/change-registry.ts`:

- **`LOGIC_CHANGE_LOG`** — реестр всех аудит-правок логики (не UI, не
  косметика) с полями `id`, `date`, `description`, `filesChanged`,
  `frozenAtMs`.
- **`currentFreezeMs(log)`** — момент заморозки ДЕЙСТВУЮЩЕГО набора правил
  в целом (максимум по всем записям). Система оценивается как единое
  целое: последняя правка сбрасывает часы для всех, потому что правки
  взаимодействуют друг с другом (пример: `spread-balance-parity` меняет,
  какие сделки вообще попадают в `'win'`/`'loss'`, что напрямую влияет на
  выборку, от которой `wilson-min-samples` считает свою границу).
- **`isForwardTestTrade(entryTimeSec, freezeAtMs)`** — сделка засчитывается
  как честный форвард-тест, только если время её входа `>= freezeAtMs`.
- **`computeForwardTestReport(trades, freezeAtMs, profitPercent)`** —
  считает метрики только по форвард-сделкам и выносит вердикт:
  `insufficient-data` / `below-breakeven` /
  `above-breakeven-not-significant` / `significantly-above-breakeven`.
  Порог достаточности выборки переиспользует уже существующий
  `MIN_THRESHOLD_BACKTEST_SAMPLES=20` (`threshold-calibration.ts`), а не
  изобретает новую константу. Точка безубыточности и статистическая
  значимость считаются теми же функциями (`breakevenWinRateFromProfitPercent`,
  `wilsonLowerBound`), что и в `pattern-reliability-calibration.ts` — чтобы
  не повторить ту же ошибку, которую чинили эти же правки (дублирование
  экономической логики с риском разъехаться).

`npm run backtest` теперь всегда печатает и сохраняет секцию
**FORWARD-TEST** в дополнение к обычному IN-SAMPLE/OUT-OF-SAMPLE отчёту —
с явным предупреждением, что ретроспективный бэктест НЕ подтверждает
прибыльность вперёд, если форвард-сделок ещё недостаточно (что на момент
написания этого документа — всегда, так как ни у одной правки в реестре
ещё не прошло реального времени).

## Правила ведения `LOGIC_CHANGE_LOG`

1. **Дата заморозки — момент деплоя, не задним числом.** Если правка
   меняется повторно (даже "докручивается"), `frozenAtMs` переносится на
   новый момент — накопленный до этого форвард-тест относится к СТАРОЙ
   версии правила и не может быть выдан за подтверждение новой.
2. **Каждая логическая правка (не косметика/UI-текст) — новая запись.**
   Правки порогов, множителей, формул исхода сделки, констант экономики —
   входят. Переименование переменной, правка комментария, рефакторинг без
   изменения поведения — не входят.
3. **Минимум `MIN_THRESHOLD_BACKTEST_SAMPLES` (20) решённых сделок ПОСЛЕ
   даты заморозки**, прежде чем `computeForwardTestReport` перестанет
   возвращать `insufficient-data`. До этого момента **никакие выводы о
   прибыльности текущей логики недопустимы** — ни "выглядит лучше", ни
   "выглядит хуже".
4. **Форвард-тест оценивает ДЕЙСТВУЮЩИЙ набор правил целиком**, не каждую
   правку изолированно — см. `currentFreezeMs()`. Изолированная оценка
   одной правки потребовала бы знать, какие именно исторические данные
   были у её автора перед глазами, что на практике невоспроизводимо и
   создавало бы ложное чувство точности.
5. При добавлении записи в реестр — обновить и changelog-файл
   (`docs/changelog/CHANGES_APPLIED_*.md`) с той же датой; `id` записи в
   реестре должен быть узнаваем по имени файла changelog.

## Экономика бэктеста согласована с реальным демо-счётом (2026-09-13, отдельный фикс)

Ранее в этом разделе было зафиксировано ограничение: `backtest/metrics.ts`
считал доходность в R-мультипликаторах (`WIN_R=2`/`LOSS_R=-1` — модель со
стоп-лоссом/тейк-профитом 2:1), тогда как реальный демо-счёт и калибровка
используют экономику бинарных контрактов с фиксированной выплатой
`profitPercent`. Это устранено:

- `computeMetrics(trades, profitPercent)` теперь считает `win -> +profitPercent/100`,
  `loss -> -1`, `timeout -> 0` — те же единицы (доля от ставки), что и
  `pnl` на реальном демо-счёте. `computeSplitMetrics`/`computeMetricsBySession`
  принимают `profitPercent` тем же способом.
- Непрерывное вычитание `spreadCostR` из R убрано: в контракте с
  фиксированной выплатой payout не масштабируется от того, насколько
  сильно цена прошла порог, — реальная стоимость спреда уже полностью
  учтена выше по пайплайну (`applySpreadToOutcome()` переразмечает
  пограничные `'win'` в `'timeout'` до того, как сделка попадает в
  метрики). `spreadCostR` остаётся per-trade диагностическим полем в
  отчёте, но больше не входит в расчёт доходности — иначе стоимость
  спреда учитывалась бы дважды.
- Заодно исправлено смежное расхождение: `winRate` в `BacktestMetrics`
  раньше делил на `total` (включая timeouts) — единственное место в
  проекте, считавшее винрейт так; теперь везде `wins/(wins+losses)`, как в
  `useAnalyticsStore` и в вердикте форвард-теста.
- `--profit-percent` в CLI (`npm run backtest`) теперь единообразно
  управляет и точкой безубыточности форвард-теста, и самой доходностью
  во всех метриках, вместо двух независимых допущений об экономике счёта.
  Payout явно печатается в шапке каждого отчёта.
- Поля интерфейса (`averageR`, `maxDrawdownR`) не переименованы, чтобы не
  расширять правку на JSON-схему без отдельного решения, но подписи в
  отчётах изменены на "Average Return"/"Max Drawdown" с единицей `/stake`
  вместо вводящего в заблуждение `R`.

См. `docs/changelog/CHANGES_APPLIED_BACKTEST_PAYOUT_ECONOMICS_20260913.md`.

## Как запускать

```bash
npm run backtest -- --symbol=EURUSD --from=2026-01-01 --to=2026-09-01 \
  --freeze-at=2026-09-13 --profit-percent=80
```

`--freeze-at` необязателен — по умолчанию используется
`currentFreezeMs(LOGIC_CHANGE_LOG)` (момент заморозки действующего набора
правок). Указывать вручную имеет смысл только для ретроспективного анализа
более старой версии правил.

## Horizon-аудит: независимость наблюдений и безубыточность (2026-09-20)

Форвард-тест (выше) защищает от переобучения **правил**. Отдельная защита нужна внутри самого horizon-audit — от завышения значимости:

1. **Независимость.** Решения принимаются по дедуплицированным наблюдениям (`--dedupe-scope=pool`, консервативно: сигналы разных инструментов пула в пределах горизонта — одно событие). Сырые p-value остаются в отчёте только для сравнения.
2. **Безубыточность.** Допуск — нижняя граница Уилсона строго выше `max(100/(100+payout), дрейф-baseline)`, а не выше 50%.
3. **Нулевой тест.** `npm run backtest:null-audit` прогоняет тот же конвейер на случайном блуждании; появление `valid` означает утечку в методологии и завершается кодом 1. Прогонять после любой правки `horizon-audit.ts` / `horizon-verdict.ts`.
4. **Версия алгоритма.** Любая правка детекторов или набора индикаторов аудита поднимает `OCCURRENCE_ALGORITHM_VERSION`; таблицу горизонтов нельзя генерировать из отчёта другой версии (`--check` падает).
5. Изменение таблицы горизонтов, влияющее на подавление сигналов, — логическая правка: запись в `LOGIC_CHANGE_LOG` (см. правила выше).
