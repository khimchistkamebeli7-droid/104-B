# Аудит модуля "гармонические паттерны" на синтетических данных

**Дата:** 2026-09-11
**Объекты:** `src/compute/patterns/harmonic-pattern.ts`, `src/compute/indicators/zigzag.ts`
**Метод:** синтетический генератор OHLCV со встроенным ground truth (10 паттернов:
Gartley/Bat/Crab/Butterfly/AB=CD × {buy, sell}) + прямая проверка детектора +
полный прогон через `simulate()` → `computeSplitMetrics()` → `generateReport()`.

## Новые файлы

- `backtest/synthetic/harmonic-data.ts` — генератор. Фибо-коэффициенты каждого
  типа подобраны алгебраически (`cd = ad − ab + bc`) так, чтобы одновременно
  проходить все 4 проверки (`ab_xa`, `bc_ab`, `cd_bc`, `ad_xa`) с запасом ≥30%
  ширины допуска — на "идеальном" (безшумовом) паттерне confidence ≈ 0.99+.
- `backtest/harmonic-audit.ts` — исполняемый скрипт (`npm run
  backtest:harmonic-audit`): (1) прямая проверка `detectHarmonicPattern` по
  каждому внедрённому паттерну (тип/направление/PRZ/SL/TP, ложные срабатывания
  до подтверждения D), (2) полный прогон через существующую инфраструктуру
  бэктестинга (`simulate`, `computeSplitMetrics`, `generateReport`) — отчёты
  сохраняются в `backtest/output/backtest-SYNTH-HARMONIC-1m.{md,json}`.

## Найденные и исправленные проблемы

### 1. (РЕАЛЬНЫЙ БАГ, исправлено) HTF-группировка ZigZag привязана к позиции
### в массиве, а не к абсолютному времени свечи

**Файл:** `src/compute/indicators/zigzag.ts`, `findHarmonicZigZagPoints()`.

`resampleCandles()` группирует свечи блоками по `htfFactor` (5) НАЧИНАЯ С
ИНДЕКСА 0 переданного массива. Production и бэктест передают в детектор
СКОЛЬЗЯЩЕЕ окно (`candles.slice(i - windowSize + 1, i + 1)`), начало которого
сдвигается на 1 свечу каждый бар. Из-за этого граница HTF-группы для ОДНИХ И
ТЕХ ЖЕ исторических свечей "гуляла" в зависимости от `i % htfFactor`.

**Наблюдаемый эффект (до фикса):** на неизменной рыночной структуре, без
единого реального изменения цены, детектор на 9 последовательных барах подряд
возвращал 5 РАЗНЫХ значений времени/PRZ/SL/TP для одного и того же
паттерна — то есть точка D, зона разворота и уровни стопа/цели "прыгали" на
графике исключительно из-за фазы скользящего окна.

**Фикс:** перед ресэмплингом отбрасываем не более `htfFactor − 1` первых
свечей так, чтобы группировка начиналась с ближайшей свечи, чьё время кратно
`htfFactor × barSeconds` — то есть привязываем группировку к абсолютному
времени, а не к позиции в срезе. Изменение сделано ЛОКАЛЬНО для гармоник
(`alignToAbsoluteHtfBoundary()` внутри `zigzag.ts`), не трогая сам
`resampleCandles()`, которым также пользуются уже проверенные
`order-block-nested.ts`/`fvg-nested.ts` (у них другой паттерн использования,
трогать их поведение вне рамок этого аудита не стали).

**Проверено:** после фикса `res.time` стабилен на всех барах подтверждения
(было: 5 разных значений на 9 барах → стало: 1 значение на всех 9). Полный
набор тестов (815/815, включая `harmonic-pattern.test.ts` и `zigzag.test.ts`)
проходит без изменений.

### 2. (РЕАЛЬНЫЙ БАГ, исправлено) PRZ для ab-cd считался от неверной ноги

**Файл:** `src/compute/patterns/harmonic-pattern.ts`, `evaluateWindow()`
(проекция CD в блоке PRZ).

Для типов Gartley/Bat/Crab/Butterfly PRZ строится как `C.price + cdSign ×
cdRange × BC` — это корректно, т.к. `matchXabcd` проверяет соотношение
`CD/BC`. Но для `ab-cd` код ошибочно использовал ТУ ЖЕ формулу с базой `BC`,
хотя `matchAbCd` проверяет совсем другое соотношение — `CD/AB ≈ 1.0`
(`cdAb = cd/ab`, см. `scoreAgainstPoint(cdAb, 1, tolerancePct)`). Поскольку
BC — самостоятельная ретрейс-нога (обычно 40-90% от AB, а не равна ей), PRZ
систематически уезжал от реальной точки D на `|AB − BC|`.

**Наблюдаемый эффект (до фикса):** на синтетических данных PRZ для ab-cd был
смещён от истинного D на ~900 пунктов при цене ~50000 (т.е. ~1.8%) — во всех
10 проверенных ab-cd сетапах (buy и sell) PRZ НЕ содержал точку D вообще.
Практическое следствие: любая логика, полагающаяся на попадание цены в PRZ
для ab-cd (например, `checkPrzConfluence` — подтверждение по свежим OB/FVG
внутри зоны), работала на заведомо неверной зоне.

**Фикс:** для ветки `ab-cd` база проекции CD — `AB` (`legLength(A, B)`), а не
`BC`. Остальные 4 типа не затронуты (их формула была верна).

**Проверено:** остаточное расхождение PRZ↔D для ab-cd упало с ~900 до ~5
пунктов (это уже обычный шум округления HTF-группировки, а не структурная
ошибка). Тесты `harmonic-pattern.test.ts` (14/14) и `trade-levels.test.ts`
(10/10) проходят без изменений — существующие фикстуры не покрывали этот
конкретный количественный кейс с достаточно большой разницей AB/BC, поэтому
баг не был виден на них.

### 3. Ошибки генератора синтетических данных (не баг приложения)

В процессе построения ground truth для аудита были обнаружены и исправлены
2 бага в самом генераторе (`backtest/synthetic/harmonic-data.ts`), из-за
которых 3 из 10 паттернов изначально не подтверждались:

- Шумовой "gap"-участок между паттернами был центрирован ровно на цене D, что
  иногда позволяло шуму чуть превысить саму точку D до начала настоящего
  разворота — ZigZag в этом случае регистрировал паразитную вторичную
  pivot-точку рядом с D вместо самой D. Убрали gap — разделения "мостом"
  между паттернами достаточно.
- Финальный "мост", подтверждающий D последнего паттерна в последовательности,
  был направлен в неверную сторону для одной из двух ориентаций (знак был
  противоположным требуемому) — цена не уходила от D в сторону,
  необходимую для его подтверждения. Исправлен знак.

## Важное для интерпретации любых бэктестов гармоник в этом проекте

`resolveOutcome()`/`applySpreadToOutcome()` (уже задокументированное,
намеренное поведение всего движка, не специфичное для гармоник) резолвят
исход КАЖДОГО сигнала по направлению закрытия СЛЕДУЮЩЕЙ свечи после входа —
`harmonicStop`/`harmonicTarget`/PRZ, которые считает детектор, НЕ участвуют в
резолвинге исхода вообще. Поэтому R-мультипликаторы бэктеста отражают
точность краткосрочного (1 бар) предсказания направления, а не то, был бы
реально достигнут structural TP раньше structural SL. Высокий win-rate на
синтетических данных (97-100%) в первую очередь подтверждает, что модуль
корректно определяет НАПРАВЛЕНИЕ разворота — это ожидаемо и не является
самостоятельным доказательством прибыльности структурных уровней SL/TP.

  соответствуют стандартной методологии (Carney).

  `harmonicFibTolerancePct`, `harmonicMinRR`) корректно прокинута из
  `DEFAULT_INDICATOR_CONFIG` через `backtest/config.ts` и
  `full-snapshot.ts` — до этого аудита уже была исправлена (см. комментарии
  в коде с предыдущими датами аудита).
- Freshness-гейт (`ageBars`/`maxAgeBars`) и множественные скользящие окна
  (`windows` — 3 варианта хвоста ZigZag) — работают как задокументировано.
