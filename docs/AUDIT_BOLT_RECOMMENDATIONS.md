# Рекомендации для bolt.new — сборка, тестирование, деплой без нареканий

Этот проект (`trading-pwa-terminal`) уже хорошо структурирован
(Vite + React 18 + TypeScript + Zustand + Supabase + Web Worker для
тяжёлых вычислений + Playwright e2e), но у него нестандартный для
bolt.new состав шагов сборки. Ниже — конкретные указания, чтобы bolt.new
собрал, протестировал и задеплоил его без ошибок.

---

## 1. Обязательная последовательность команд

Проект уже определяет правильный CI-скрипт в `package.json`:

```bash
npm install
npm run ci        # = npm run typecheck && npm run lint && npm run test
npm run build      # = tsc --noEmit -p tsconfig.app.json && vite build
```

**Важно для bolt.new: `npm run build` включает в себя `tsc --noEmit`
перед `vite build`.** Это значит, что сборка провалится при ЛЮБОЙ
ошибке типизации, даже если сам Vite/esbuild мог бы молча
транспилировать файл. Это осознанное решение проекта (строгий контроль
качества) — **не убирайте `tsc --noEmit` из скрипта `build`, даже если
кажется, что это «ускорит» сборку**. Если типизация не проходит, чинить
типы, а не обходить проверку.

Рекомендуемый порядок для bolt.new при каждой генерации/правке кода:

1. `npm run typecheck` — быстрая проверка типов без полной сборки.
2. `npm run lint` — ESLint (`eslint.config.js`, flat config, ESLint 9).
3. `npm run test` — Vitest, **622 теста** (по состоянию на 2026-08-30,
   проверено реальным прогоном), ожидаемый результат:
   `Test Files: 48 passed | Tests: 622 passed`. Если после генерации
   кода видите `X failed`, значит только что внесённое изменение
   сломало существующий контракт — чинить нужно **логику**, а не
   тест (если только тест сам не оказался устаревшим — тогда явно
   написать в ответе пользователю, почему тест меняется).
4. `npm run build` — типы + продакшн-сборка.
5. (Опционально, но рекомендуется перед публикацией) `npm run e2e` —
   Playwright, требует установленных браузеров:
   `npx playwright install --with-deps chromium`.

## 2. Переменные окружения — без них часть функциональности не работает

Файл `.env.example` уже перечисляет всё нужное. bolt.new должен
попросить пользователя задать реальные значения (или создать
Supabase-проект через интеграцию bolt.new с Supabase, если она
подключена) **до** первого деплоя:

```
VITE_SUPABASE_URL=              # обязательно для персистентности сигналов/калибровки и всех proxy-* edge-функций
VITE_SUPABASE_ANON_KEY=         # обязательно, тот же смысл
VITE_DERIV_APP_ID=1089          # есть дефолт, можно не трогать для разработки
VITE_SENTRY_DSN=                # опционально — без него initSentry() просто не активируется, ошибки идут в console.error
VITE_YAHOO_PROXY_URL=           # обязательно только если используется источник Yahoo
```

Приложение **не падает** без Supabase (весь код в `src/lib/
signal-persistence.ts` заворачивает операции в `isSupabaseConfigured`
и тихо no-op'ает), но без него:
- история сигналов не персистится в БД (остаётся только в
  `localStorage` через zustand `persist`);
- калибровочная модель не сохраняется между устройствами;
- источники котировок, которые ходят через edge-функции-прокси
  (`finnhub`, `twelvedata`, `yahoo`, `gemini`-анализ), не работают
  вообще — они физически не могут получить API-ключ без Supabase.

**Рекомендация bolt.new:** если пользователь не подключил Supabase,
явно предупредить его в чате, что часть источников данных и
персистентность будут недоступны, а не собирать молча «наполовину
рабочее» приложение.

## 3. Supabase-миграции нужно применять отдельно от фронтенд-сборки

`npm run build` **не трогает** Supabase вообще — миграции в
`supabase/migrations/*.sql` не применяются автоматически ни `npm
install`, ни `vite build`. Если bolt.new имеет встроенную интеграцию с
Supabase (создание проекта / применение миграций из UI) — использовать
её и применить **все** файлы из `supabase/migrations/` по порядку имён
(они уже названы с timestamp-префиксом, сортировка по алфавиту = по
времени), включая новый файл из этого аудита:
`20260828120000_lock_down_signals_and_calibration_delete.sql`.

Если такой интеграции нет — явно сказать пользователю выполнить
`supabase db push` (или применить SQL-файлы вручную через Dashboard →
SQL Editor) **до** того, как объявлять деплой готовым, и отдельно
задеплоить `supabase/functions/*` (включая новую
`delete-all-signals`) через `supabase functions deploy`.

Секреты для edge-функций (`TWELVEDATA_API_KEY`, `FINNHUB_API_KEY`,
`GEMINI_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) задаются в Supabase
Dashboard → Edge Functions → Secrets, **не** через `.env` фронтенда —
это разные рантаймы (Deno на сервере vs Vite-бандл в браузере), и
попадание `SERVICE_ROLE_KEY` в `.env`/клиентский бандл было бы
серьёзной дырой безопасности (полный обход RLS с публичным ключом).

## 4. PWA-специфика — что проверить после каждой сборки

Этот проект — устанавливаемое PWA (`vite-plugin-pwa`), поэтому после
`npm run build` стоит проверять не только «собралось без ошибок», но и:

- `dist/manifest.webmanifest` ссылается только на файлы, которые
  реально лежат в `dist/` (после этого аудита — `icon-192.png`,
  `icon-512.png`, `icon-512-maskable.png` уже на месте; если в
  будущем меняется набор иконок в манифесте — обязательно добавлять
  сами файлы в `public/`, иначе регрессия к исходному багу #1).
- `dist/sw.js` генерируется (`generateSW` от `vite-plugin-pwa`) и не
  превышает `maximumFileSizeToCacheInBytes` (сейчас 5 MB на файл).
- Прогнать Lighthouse PWA-аудит (Chrome DevTools → Lighthouse →
  Progressive Web App) на собранном `dist/` через `npm run preview` —
  критерий installability должен быть зелёным. Если bolt.new может
  запускать Lighthouse CI — стоит добавить это отдельным шагом после
  `npm run build`, а не полагаться только на отсутствие ошибок сборки:
  Vite не проверяет, что иконки манифеста физически существуют, сборка
  «успешно» проходит даже с битыми ссылками (это и было причиной
  исходного бага).

## 5. Bundle size budget

После фикса #4 из аудита (`manualChunks` для `lightweight-charts` /
`@sentry/react`) размер основного чанка должен заметно снизиться
относительно исходных 846 KB. Если bolt.new (или сам разработчик)
добавляет новые тяжёлые зависимости в будущем — проверять вывод `vite
build` на предупреждение
`(!) Some chunks are larger than 500 kB after minification` и по
возможности сразу добавлять новый тяжёлый пакет в `manualChunks` в
`vite.config.ts`, а не оставлять расти основной чанк дальше.

## 6. Мобильное тестирование

`e2e/terminal.spec.ts` уже использует `@axe-core/playwright` для
a11y-проверок. Рекомендуется, чтобы CI/bolt.new прогонял Playwright
хотя бы с одним мобильным профилем (`playwright.config.ts` — проверить,
настроены ли там `devices['iPhone 13']`/аналоги; если нет — добавить
проект с мобильным viewport, чтобы e2e реально покрывал `MobileNav`,
safe-area и drawer-навигацию, а не только desktop-раскладку).

## 7. Итоговый чек-лист перед тем, как считать деплой готовым

- [ ] `npm run ci` (typecheck + lint + test) — зелёный, 622/622 тестов.
- [ ] `npm run build` — без ошибок и без предупреждения о размере чанка
      выше бюджета.
- [ ] Все файлы из `supabase/migrations/` применены к реальному
      Supabase-проекту, включая
      `20260828120000_lock_down_signals_and_calibration_delete.sql`.
- [ ] Все edge-функции из `supabase/functions/` задеплоены, включая
      новую `delete-all-signals`; секреты (`*_API_KEY`,
      `SUPABASE_SERVICE_ROLE_KEY`) заданы в Supabase, не во фронтенд-`.env`.
- [ ] `.env`/переменные окружения bolt.new реально заполнены
      (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` как минимум).
- [ ] Lighthouse PWA-аудит на собранном `dist/` — installability
      зелёный (иконки манифеста существуют и загружаются).
- [ ] `npm run e2e` — хотя бы дымовой прогон, если у окружения есть
      возможность установить браузеры Playwright.
