## Нюанс 1 (QA) — routing калибровочной модели по symbolId был неявным

**Было**: `engine.ts::recordOutcome()` всегда писал обучающий сэмпл в
`this.calibration` — модель, которую движку последней подставил
`setCalibration()` (т.е. модель ТЕКУЩЕГО активного символа). Отдельно
`tick-store/outcomes.ts` искал модель по `signal.symbolId` через
`deps.getCalibrationModel()` — но использовал этот результат только
для `triggerRetrain`, а не для самого `addSample`. Корректность (что
`this.calibration` в момент вызова и есть модель `signal.symbolId`)
держалась на инварианте ДРУГОГО модуля — `useTickStore.start()`
дренирует и заново засеивает `outcomeScheduler` только сигналами
целевого инструмента при каждой смене символа, — а не проверялась
явно там, где сэмпл реально пишется. На практике это не приводило к
багу (инвариант в коде держится), но не было ни зафиксировано тестом,
ни защищено на уровне сигнатуры.

**Стало**:
- `engine.ts::recordOutcome(signal, outcome, calibrationModel?)` —
  третий параметр (необязательный, по умолчанию — прежний
  `this.calibration`, ради обратной совместимости) — теперь именно он
  используется для `addSample`, а не поле движка.
- `tick-store/outcomes.ts` ищет модель по `signal.symbolId` ОДИН раз и
  передаёт её явным аргументом и в `recordOutcome`, и в
  `triggerRetrain` — один и тот же объект в обоих местах, а не два
  независимых источника, которые до этого технически могли разойтись.
- Добавлены тесты:
  - `engine.test.ts`: явный `calibrationModel`-параметр пишет сэмпл
    именно в переданную модель, а не в `this.calibration`, даже когда
    обе заданы и различны; при `null` — сэмпл никуда не пишется, даже
    если `this.calibration` установлен; при отсутствии параметра —
    поведение как раньше (back-compat).
  - `tick-store/outcomes.test.ts`: сценарий с ДВУМЯ сигналами разных
    инструментов (BTCUSDT + EURUSD), резолвящимися в одном вызове
    `maybeResolveOutcomes` — проверяет, что `recordOutcome()` для
    каждого получает модель именно СВОЕГО инструмента третьим
    аргументом, а не общую/перепутанную.

Ничего в поведении для пользователя не меняется — это укрепление
инварианта, который и так соблюдался, на уровне кода и тестов, а не
исправление наблюдаемого бага.

## Нюанс 2 (инфраструктура/безопасность) — дефолт-константа в `calibration_state.id`

**Было**: миграция `20260906120000_calibration_state_per_symbol.sql`
перенесла PK на `symbol_id`, но не трогала `DEFAULT` столбца `id` —
он остался равен фиксированной константе
`'00000000-0000-0000-0000-000000000001'` (наследие исходной
singleton-схемы). Столбец `id` нигде не читается/не пишется клиентом
(`saveCalibrationState`/`loadCalibrationStateFromDb` работают только
через `symbol_id`) — риска для данных нет, но у ВСЕХ новых строк
(EURUSD и т.д.) было бы одинаковое, похожее на PK значение —
вводит в заблуждение при просмотре таблицы напрямую.

**Стало**: новая миграция
`20260906130000_calibration_state_id_default_hygiene.sql` меняет
`DEFAULT` на `gen_random_uuid()` (встроена в Postgres 13+, расширения
не требуются). Существующие строки не трогаются — только дефолт для
будущих вставок.
