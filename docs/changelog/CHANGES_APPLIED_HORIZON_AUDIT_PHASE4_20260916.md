## Обновление 2026-09-18 (v1.5 — слияние веток и исправление найденных дефектов)

Две ветки проекта разошлись: одна закрыла Фазу A′ (производительность бэктеста, кэш,
golden-тест), другая — Фазу B (генерация runtime-таблицы, проводка, реальные прогоны).

Ни одна не удовлетворяла Definition of Done. Ветки слиты, при сверке найдены и
исправлены дефекты, перечисленные ниже. Каждый пункт — правка поведения, а не
переформулировка.

### 1. Look-ahead в индикаторной серии бэктеста (исправлено)

`computeIndicatorsSeries()` в `horizon-audit.ts` брала `atr`, `adx`, `vwap`,
`meanReversionRsi`, `impulseVelocity`, `volumeProfilePoc` из `snapshot`, то есть из
значения **последнего бара всего датасета**, и ставила это значение на каждый бар.
`IndicatorSeries` не содержит поля `atr` вовсе, поэтому `series.atr?.[i] ?? snapshot.atr`
всегда уходил в правую ветку.

Масштаб фактического ущерба меньше, чем кажется на первый взгляд, и это важно
зафиксировать честно: `buildOccurrences` получает `activeFeatures`, состоящий только из
имён паттернов, а гейтинг в `computeIndicators` включает ATR/ADX/VWAP только по
индикаторным фичам. Поэтому в уже сохранённых прогонах эти поля были `null` и в старом
коде тоже, а реально протекал только `meanReversionRsi` (через `mean-reversion`, у
которого в этих прогонах не было ни одного срабатывания). То есть **закоммиченные
результаты не контаминированы**, но при первом же прогоне с индикаторными фичами утечка
сработала бы молча.

Функция удалена. Бэктест переведён на причинные `computeIndicatorSeriesRaw()` /
`snapshotFromSeries()` из `src/compute/IndicatorAggregator.ts`. Не причинные поля
(`vwap`, `volumeProfilePoc`, `impulseVelocity`) отдаются `null` явно — их единственный
потребитель `signal-builder.ts::buildFeatureVector` в бэктесте не вызывается.

Отдельно зафиксировано: переход на полномассивный прогрев **не эквивалентен** прежнему
расчёту на `windowSize`-срезе. Рекурсивные сглаживания Уайлдера (RSI/ATR/ADX) и EMA
раньше прогревались от бара `i − windowSize + 1`, теперь — от бара 0. Расхождение
экспоненциально затухает и на `windowSize=500` лежит в шуме, но это смена поведения в
лучшую сторону, а не «оптимизация без изменения результата».

Golden-тест переписан: прежняя версия фиксировала поведение на `activeFeatures =
['inside-bar']` — чисто ценовом паттерне, который индикаторы не читает, — и потому не
проверяла тот путь, ради которого писалась. Новый тест сравнивает снапшот на баре `i`
для полного массива и для массива, обрезанного по `i`: любой broadcast значения
последнего бара ловится мгновенно.

### 2. `holmBonferroni()` — две ошибки в одной функции (исправлено)

Первая: затиралось направленное условие. `significance.ts` определяет `significant` как
«p < alpha **и** accuracy > baseline», а `holmBonferroni` присваивала
`significant = pValue <= threshold`, теряя вторую половину. В `backtest/output`
из-за этого лежит `impulse-breakout` с `testAccuracy: 0.4635` и `significant: true` —
паттерн, значимо **хуже** случайного, помечен как значимый.

Вторая: не было шага вниз. Процедура Холма обязана остановиться на первом
неотвержении; прежняя версия проверяла каждую позицию независимо.

Переписывать уже сохранённые отчёты задним числом нельзя, поэтому
`generate-pattern-horizon-table.ts` перепроверяет направление сам, из
`pValue` + `testAccuracy`, и не доверяет полю `significant` на входе.

### 3. Таблица горизонтов скоупнута по классу актива (исправлено)

Правило слияния «valid бьёт не-valid» применялось поверх разных классов активов. На
закоммиченных данных это давало прямое противоречие: `harmonic-pattern` валиден на
BTCUSDT/ETHUSDT (55.07%, n=670), и он же на EURUSD/USDJPY того же периода даёт 43.98%
при n=407 и p=0.0172 — значимо в проигрышную сторону. В рантайм уходили крипто-30
баров на оба класса, то есть на EURUSD ставился откалиброванный горизонт для паттерна,
который в том же прогоне проигрывал.

Таблица теперь `Record<AssetClass, Partial<Record<PatternName, …>>>`,
`signal-builder.ts` передаёт `assetClassOf(symbolId)`. Смешанный по классам пул
генератор пропускает с предупреждением: разложить такой отчёт обратно невозможно.

### 4. Третий статус `no-evidence` (исправлено)

Прежняя схема имела два статуса, и `significant === false` давало `rejected`, а
`signal-builder` на `rejected` возвращал `null`. Это подмена «нет доказательств» на
«доказано обратное». На закоммиченных данных честная перегенерация выключила бы
`inside-bar` (n=6166, p=0.87), `strong-order-block-reaction` (n=3439, p=0.95) и
`order-block-continuation` (n=925, p=0.32) — три рабочие стратегии, про которые данные
говорят лишь «не отличается от монетки на этом объёме».

Теперь: `valid` — значимо вверх + Wilson pass; `rejected` — значимо **вниз**
(`p <= alpha`, `accuracy < 0.5`), только это подавляет сигнал; `no-evidence` — всё
остальное, включая «значимо вверх, но без Wilson» (такой паттерн не следует выключать,
его следует не калибровать).

Асимметрия поправки на множественные сравнения сознательная и задокументирована в коде:
для допуска используется Holm-скорректированная значимость, для защитного отказа —
сырая alpha. Ложное срабатывание защиты стоит одного подавленного сигнала, ложный
допуск стоит денег.

### 5. Закоммиченная таблица не соответствовала своему генератору (исправлено)

Файл `src/decision/pattern-horizon-table.ts` был помечен «АВТОГЕНЕРИРОВАНО», но прогон
генератора по закоммиченным отчётам давал 5 записей вместо 2, и `impulse-breakout` с
другим горизонтом (2 бара из форекс-прогона вместо 3 из крипто-). То есть файл был
отредактирован вручную или сгенерирован другой версией скрипта.

Добавлен режим `--check` и шаг `npm run backtest:gen-horizon-table:check` в
`npm run ci`: расхождение таблицы с `backtest/output` теперь падает в CI, а не
обнаруживается следующей ревизией.

Попутно в генераторе: детерминированная сортировка файлов и ключей (раньше порядок
слияния зависел от `readdir()`), учёт `setupType` (раньше строки с одним
`patternName` и разными `setupType` схлопывались молча), независимость от CWD,
экранирование строк, пустая таблица вместо падения при отсутствии отчётов.

### 6. Инженерная гигиена

- `backtest/` возвращён под ESLint (`no-console` выключен точечно для CLI-скриптов). Именно игнор всего каталога позволил прожить незамеченными и утечке из п.1, и объявлению на нулевой колонке внутри функции.

Прежний инлайновый кэш ключевался только по символу/таймфрейму/диапазону/окну и не инвалидировался при смене конфига или набора фич. Введена `OCCURRENCE_ALGORITHM_VERSION`.

3. Паттерн `impulse-breakout` показывает `46.3%` accuracy при `p=0.0061`, но **не проходит Wilson gate**: это не баг, а корректная отсечка именно по защитному критерию, чтобы не принимать статистически слабый сигнал из-за малого/смещённого пула.
4. `order-block-nested` — ещё один пример корректной фильтрации: на малой выборке (`n=4`) Wilson LB внезапно высокий, но из-за малой n и реального переоценивания на фоне `significant`/`not significant` на всех пулах он не считается валидным.
5. Поведение `harmonic-pattern` и `impulse-breakout` подтверждает, что таблица и фильтр `isPatternHorizonRejected()` работают по принципу “только валидные + Wilson-pass” и не дают ложных допусков.

## Обновление 2026-09-17 (v1.3 — исправление walk-forward)

При независимой построчной проверке v1.2 обнаружен и исправлен содержательный баг в реализации walk-forward — **не косметика, а неверная статистическая методология**, требующая перепрогона любых уже сохранённых результатов с `--split=walkforward` (в этом репозитории таких сохранённых прогонов не было — `backtest/output/` не существовал, повторный прогон не отменяет никаких опубликованных чисел).

**В чём была ошибка**: `assignWalkForwardPartitions()` делила КАЖДЫЙ fold **локально** на "первые `purgeSeconds` = train" / "остальное = test", не используя предыдущие folds как обучающую выборку для последующих. Формулировка в разделе v1.2 выше ("purge-зазор между train и test **внутри каждого фолда**") точно описывает то, что было реализовано — и то, что оказалось неверным: при `purge=0` (значение по умолчанию для быстрых прогонов) это давало **ВСЕ** наблюдения как test и **НИ ОДНОГО** как train — `bestExpiryBars` для большинства folds не мог быть выбран вообще, а `horizon-partitioning.test.ts` v1.2 проверял именно это (ошибочное) поведение как ожидаемое, поэтому тесты проходили и баг не был замечен.

**Что исправлено**:
1. `assignWalkForwardPartitions()` заменена на пару `computeFoldBoundaries()` + `assignFoldIndex()` — folds теперь только размечают, к какому хронологическому окну относится каждое наблюдение (`o.fold`), без назначения train/test.
2. Настоящая walk-forward логика — новая функция `computeWalkForwardResult()` в `horizon-audit.ts`: для fold `k` (кроме fold 0, у которого нет предыстории) train = **все** occurrences из folds `< k` (с purge-отступом перед границей k), test = occurrences fold `k`. `bestExpiryBars` выбирается **только** по train этого конкретного fold — не по всем данным сразу (иначе выбор подглядывает в test). Тестовые исходы аккумулируются по всем оценённым folds в один пул, который и идёт в биномиальный тест/Wilson-гейт — это даёт обещанный ~4-кратный прирост эффективной test-выборки (out-of-sample почти вся история, кроме fold 0, а не только последние 20%).
3. `pattern-audit-checklist-variant-B.md`/итоговый `bestExpiryBars` для walk-forward теперь — мода (самый частый выбор) по фолдам, а не число с единственного прогона; полная разбивка по фолдам сохраняется в `PatternResult_.perFold` и выводится отдельным разделом в markdown-отчёте (`## Разбивка по folds`) — если `bestExpiryBars` заметно "прыгает" между folds, это видно явно, а не скрыто за агрегатом.
4. `horizon-partitioning.test.ts` переписан — новые тесты проверяют именно инвариант, который был нарушен (train fold `k` строго больше train fold `k-1`, т.е. накопление истории, а не константный размер), плюс отдельный `horizon-audit-walkforward.test.ts` с прямыми тестами `computeWalkForwardResult()` на синтетических данных с заведомо известным правильным ответом.
5. Попутно исправлены три не связанных с walk-forward, но обнаруженных при той же построчной проверке бага: рассинхронизация имени поля `walkforwardFolds`/`walkForwardFolds` в `CliArgs` (ловится `tsc`, но конкретно в этом файле было замаскировано отсутствием прогона `tsc --noEmit` после последнего изменения интерфейса), опечатка `candles1mTotal` в JSON-метаданных (shorthand-property ссылался на несуществующую переменную вместо `totalCandles1m`), и отсутствующий локальный `import { wilsonLowerBound }` в `pattern-reliability-calibration.ts` (там был только re-export, который не вводит имя в область видимости самого файла).
6. `main()` в `horizon-audit.ts` был неусловно вызван на верхнем уровне модуля — любой `import` из файла (в том числе ради переиспользования `computeWalkForwardResult` в тестах) запускал бы весь CLI с реальными сетевыми запросами. Добавлен guard по `process.argv[1] === fileURLToPath(import.meta.url)`.

Проверено: `tsc --noEmit` (оба конфига), `npm run lint`, `npx vitest run` (70 файлов / 931 тест, включая 8 новых тестов партиционирования и 6 новых прямых тестов walk-forward-агрегации), `npm run build` — все чисто.

**Не выполнено в рамках этого исправления**: реальный прогон `--split=walkforward` на исторических данных (требует сетевого доступа к Deriv, недоступного в среде разработки) — численные результаты v1.1/v1.2 по-прежнему получены в holdout-режиме; первый содержательный прогон walk-forward ещё предстоит сделать и будет отличаться от того, что предполагалось в v1.2 (там числа для walk-forward тоже не приводились — только формулировка методологии).

## Ограничение

Deriv отдаёт максимум ~2881 1m свечей независимо от запрошенного диапазона дат. Для 1m таймфрейма это даёт ~2351 бар для детектирования (после вычета windowSize=500 и maxExpiry=30), что недостаточно для набора 200 test-исходов по большинству паттернов. Для 5m и выше после ресэмплинга свечеё ещё меньше (577 для 5m, 193 для 15m).

## Сколько данных реально необходимо

Расчёт по фактической частоте срабатываний (2351 бар детектирования, test=20%≈470 баров, порог 200 исходов):

| Паттерн | Частота | Нужно 1m баров | Дней истории |
|---|---|---|---|
| inside-bar | 9.15% | ~10 900 | 7.6 |
| strong-order-block-reaction | 2.13% | ~47 000 | 32.7 |
| impulse-breakout | 1.91% | ~52 200 | 36.3 |
| order-block-continuation | 1.70% | ~58 800 | 40.8 |
| harmonic-pattern | 1.06% | ~94 000 | 65.3 |

Оценка «≥50000 свечей / ~35 дней» верна для средних по частоте паттернов (inside-bar, strong-order-block-reaction), но для редких паттернов (pin-bar, harmonic-pattern) занижена в 2-5 раз. Наращиванием объёма одного инструмента длинный хвост не закрывается — пулинг по инструментам (Фаза 2, реализовано в v1.2) и walk-forward (Фаза 3, реализовано в v1.2) дают до ~24-кратного прироста эффективной тестовой выборки.

## Рекомендация

Для завершения Фазы 4 требуется комбинация мер (в порядке приоритета):
- **(а) Исправление пагинации data-loader** — ранний выход при `batch.length < MAX_PER_REQUEST` вероятная причина лимита 2881; поднятие `MAX_PER_REQUEST` до 5000 даёт 5× данных на запрос.
- **(б) Пулинг по 6-8 инструментам** — 6-8-кратный рост выборки без нового источника данных.
- **(в) Walk-forward** вместо одиночного holdout — ~4× эффективной test-выборки на тех же данных.
- **(г) Градуированный критерий Wilson** — допуск паттернов по нижней границе Уилсона вместо жёсткого отсечения n≥200.
- **(д) Внешний провайдер** (TwelveData/Finnhub) — только если (а) показала реальный лимит Deriv, а (б)-(г) не закрыли потребность.

Предварительные числа accuracy (где есть) не должны использоваться в проде без подтверждения на достаточном объёме данных.
