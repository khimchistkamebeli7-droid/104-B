# CHANGES_APPLIED_CALIBRATION_FACTOR_SELFLEARN_STAGE2_20260906.md

Дата: 2026-09-06.

Промт: «Этап 1 уже полностью реализован, приступай к реализации этапа 2
относительно плана из файлов» — связать `computeFactorStats()`
("АНАЛИТИКА ПО ФАКТОРАМ") с `PATTERN_RELIABILITY_MULTIPLIER`, который
раньше правился только вручную, через кнопку "Калибровать" с явным
предпросмотром "было / станет".

## Что сделано

1. **`src/lib/pattern-reliability-calibration.ts` (новый файл).**
   Чистая функция `computeReliabilitySuggestions(factorStats,
   currentOverrides?)`, которая берёт уже посчитанную (Этапом 1,
   per-symbol отфильтрованную) таблицу `АНАЛИТИКА ПО ФАКТОРАМ` и для
   каждого паттерна с `decidedCount >= MIN_FACTOR_SAMPLES` предлагает
   новый множитель по формуле из плана:
   `clamp(winRate / 0.5, 0.1, 1.5)`.

   Строка исключается из предпросмотра, если:
   - `decidedCount < MIN_FACTOR_SAMPLES` — тот же порог, что и в самой
     таблице факторов, ниже него `winRate` статистически ненадёжен;
   - имя не является `PatternName` — `computeFactorStats()` агрегирует
     ВСЕ факторы (индикаторы `rsi`/`ema`, структурные `bos`, фильтры),
     множитель существует только для паттернов;
   - паттерн входит в `STRATEGY_BONUS_PATTERNS`. **Важная находка при
     реализации, не упомянутая в исходном плане:** для этих 10
     паттернов (`order-block-continuation`, `fvg-nested`, ...)
     `reliabilityMultiplier` в `direction-prediction.ts` НИКОГДА не
     участвует в score — `isStrategyBonusPattern` принудительно обнуляет
     `triggerContribution` независимо от значения множителя (см. bugfix
     двойного учёта, `pattern-categories.ts` строки 36-49). Пересчёт
     множителя для них был бы мёртвым кодом, создающим иллюзию
     "самообучения" без реального эффекта на сигналы. Дополнительно их
     `sampleCount`/`decidedCount` в `computeFactorStats()` задвоены: один
     и тот же сигнал даёт ДВА `SignalFactor` с одинаковым `name` (`kind:
     'pattern'`, `contribution=0`, из `direction-prediction.ts`, и `kind:
     'strategy'` с реальным бонусом, из `signal-builder.ts`), а
     `computeFactorStats()` группирует строго по `name` без учёта `kind`
     — winRate от этого не искажается (числитель и знаменатель дублируются
     синхронно), но абсолютные счётчики — искажаются, ещё одна причина не
     доверять им здесь. Сам баг двойного счёта в `computeFactorStats()` —
     вне рамок этого прохода (Этап 1 его не касался, ломать чужой
     протестированный код без явного запроса не стал).

2. **`src/lib/pattern-categories.ts`: применение и персистентность.**
   - `RELIABILITY_MULTIPLIER_MIN`/`RELIABILITY_MULTIPLIER_MAX` (0.1/1.5)
     вынесены в константы рядом с самим `PATTERN_RELIABILITY_MULTIPLIER`
     — единая точка правды для границ клампа.
   - `applyReliabilityMultiplierUpdates(updates)` — мутирует
     `PATTERN_RELIABILITY_MULTIPLIER` **на месте** (объект и так был
     обычным мутируемым `const`, `direction-prediction.ts` читает его
     "живьём" при каждом вызове `computeDirectionScore` — новые
     множители подхватываются немедленно, без изменения сигнатур функций
     движка и без риска для существующих тестов, вызывающих его
     напрямую) и сохраняет получившийся словарь в
     `localStorage['pattern-reliability-multiplier-v1']`, чтобы
     "самообучение" не откатывалось молча при каждой перезагрузке
     страницы (тот же принцип прозрачности, что и у
     `calibration-model.ts`). Персистентные значения подгружаются и
     накладываются поверх ручных дефолтов один раз при импорте модуля.
   - `resetReliabilityOverrides()` — эскейп-люк: откатывает к снимку
     исходных ручных значений (сделанному ДО применения любых
     персистентных данных) и стирает `localStorage`-ключ. Нужен на
     случай, если автопересчёт на ещё небольшой выборке дал нежелательный
     результат.
   - Оба пути защищены от плохих значений (`NaN`/`Infinity` игнорируются,
     остальное клампится в `[0.1; 1.5]`) и от отсутствия/недоступности
     `localStorage` (SSR, приватный режим, квота) — тихий no-op вместо
     падения импорта модуля.

3. **`CalibrationPanel.tsx`: UI "было/станет".** Новый блок
   "КАЛИБРОВКА НАДЁЖНОСТИ ПАТТЕРНОВ" под таблицей
   "АНАЛИТИКА ПО ФАКТОРАМ":
   - Кнопка "Калибровать" считает предпросмотр
     (`computeReliabilitySuggestions(factorStats)`, где `factorStats` —
     уже отфильтрованные по активному символу Этапом 1) и показывает
     таблицу паттерн / N / винрейт / было / станет. Ничего не
     применяется до явного подтверждения.
   - "Применить" вызывает `applyReliabilityMultiplierUpdates` и
     показывает подтверждение; "Отмена" просто закрывает предпросмотр,
     ничего не трогая.
   - Кнопка-иконка сброса (↺) вызывает `resetReliabilityOverrides()`.
   - Явно указано в UI (не только в коде), что расчёт идёт по данным
     активного инструмента, но применяется множитель **глобально** —
     см. следующий пункт.

## Известное ограничение, оставленное явным (не молчаливым) в этом проходе

`PATTERN_RELIABILITY_MULTIPLIER` — по-прежнему единый словарь на всё
приложение, не per-symbol, в отличие от ML-модели и самой таблицы
факторов (обе стали per-symbol на Этапе 1). Это значит: если
калибровать множитель, находясь на BTCUSDT, результат будет посчитан
по данным BTCUSDT, но подставится и в trigger-контрибуцию сигналов по
EURUSD тоже. Сделать его per-symbol было архитектурно возможно, но
потребовало бы протаскивать `symbolId` через `computeDirectionScore` и
все его вызовы/тесты — риск, который выходит за рамки заявленного в
плане Этапа 2 объёма работ ("не расширяя пока саму логрегрессию... это
Этап 3"). Вместо того чтобы скрыть это ограничение, оно вынесено в
текст самой панели и сюда — по той же причине, по которой Этап 1
разводил "три смысла" одного поля: не создавать у пользователя ложное
впечатление, что число значит больше, чем оно значит на самом деле.
Кандидат на отдельный "Этап 2.1" при появлении реальной многосимвольной
торговли на разных паттернах.
