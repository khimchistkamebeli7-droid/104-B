# HTF-ресэмплинг Order Block/FVG nested-детекторов: выравнивание к абсолютному времени + асимметричные regression-тесты для гармоник — 2026-09-12

Выполнено по итогам `docs/audit/recommendations-post-harmonic-audit.md`
(документ-продолжение к `docs/audit/2026-09-harmonic-module-synthetic-audit.md`)
— обобщённым рекомендациям после точечного аудита модуля гармоник. Ниже —
что из них было реализовано в этой сессии, в порядке приоритизации из
самого документа.

## Рекомендация 3 → Рекомендация 1: эмпирическая проверка, затем фикс

**Диагноз.** `resampleCandles()` (`src/compute/patterns/fvg-strategies-shared.ts`)
группирует свечи блоками по `factor`, начиная с индекса 0 переданного
массива. `detectHtfObZones()` (`order-block-nested.ts`) и
`detectHtfFvgZones()` (`fvg-nested.ts`) вызывают её на СКОЛЬЗЯЩЕМ окне
(`candles.slice(i - windowSize + 1, i + 1)` в `backtest/simulator.ts` /
`src/engine/analysisEngine.ts`) — та же экспозиция, что уже была найдена и
исправлена для ZigZag/гармоник ранее (см. `zigzag.ts`,
`alignToAbsoluteHtfBoundary`), но не проверялась и не чинилась для этих
двух модулей.

**Эмпирическая проверка (до фикса).** Написан синтетический скрипт
(реалистичный ряд M1 с периодическими импульсами для order block и
3-свечными гэпами для FVG, epoch-aligned время — как у реальных M1-баров
брокера), прогоняющий оба детектора на 25 последовательных сдвигах
скользящего окна на 1 бар и сравнивающий строковый снимок
top/bottom/time зон в фиксированном, далёком от края окна диапазоне
истории. Результат ДО фикса: 5–6 РАЗНЫХ представлений одного и того же
диапазона на 25 сдвигах, с расхождением и во времени, и в top/bottom
(например, для order block: `bearish[107.178897-107.641074]@1735698600`
против `bearish[106.867499-107.324425]@1735699920` — сдвиг времени зоны на
1320 секунд и цены на десятые доли пункта без единого реального изменения
цены базового актива). Экспозиция подтверждена для ОБОИХ модулей.

**Фикс (Рекомендация 1, реализован как предписано — централизованно, а не
копированием по трём файлам).**
- `fvg-strategies-shared.ts`: `resampleCandles(candles, factor, options?)`
  получил опциональный `{ alignToAbsoluteTime?: boolean }` (default
  `false` — поведение по умолчанию не меняется нигде, где флаг не
  передан явно). При `true` перед группировкой отбрасывается не более
  `(factor-1)` первых свечей так, чтобы граница группы была привязана к
  свече, чьё абсолютное время кратно `factor × barSeconds`, а не к
  позиции внутри переданного среза.
- `zigzag.ts`: локальная копия `alignToAbsoluteHtfBoundary()` удалена,
  `findHarmonicZigZagPoints()` теперь вызывает
  `resampleCandles(candles, htfFactor, { alignToAbsoluteTime: true })`.
  Поведение и результат для гармоник не изменились (уже покрыто
  существующими 14 тестами `harmonic-pattern.test.ts` + 5 тестами
  `zigzag.test.ts`).
- `order-block-nested.ts` / `fvg-nested.ts`: тот же флаг включён явно в
  `detectHtfObZones()` / `detectHtfFvgZones()`. Обе функции временно
  экспортированы из своих модулей (были module-private) — по аналогии с
  уже экспортированным `computeZigZag` в `zigzag.ts` — чтобы их можно было
  проверить эмпирически напрямую, а не только через публичные
  `detectOrderBlockNested`/`detectFvgNested`.

**Эмпирическая проверка (после фикса).** Тот же скрипт, тот же диапазон
истории: ровно ОДНО представление на всех 25 сдвигах для обоих детекторов.
Дополнительно обнаружено и явно задокументировано побочное наблюдение
(не баг): часть исходной "нестабильности" при грубом сравнении полного
списка зон объясняется не дрейфом HTF-группировки, а легитимным
пересчётом `broken`-статуса order block / инвалидации FVG по мере того,
как скользящее окно открывает больше "будущей" относительно зоны цены —
зона, ещё не пробитая при меньшем окне обзора, законно может оказаться
пробитой при бóльшем. Проверено точечно: при появлении такая зона всегда
имела БИТ-В-БИТ одинаковые top/bottom (значит, дрейфа именно
top/bottom/time — того, что описано в Рекомендации 1 — нет; расхождение
только в присутствии/отсутствии зоны, что ожидаемо). Постоянный аудит-скрипт
и новые unit-тесты (см. ниже) выбирают диапазон истории достаточно далеко
от края окна, чтобы отфильтровать этот легитимный эффект и проверять
именно top/bottom/time-дрейф.

**Методология проверена в обе стороны** (важно, чтобы тест не проходил
тавтологично): временный откат фикса (`resampleCandles(candles,
HTF_FACTOR)` без опции) на тех же скриптах/тестах даёт FAIL с точным тем
же характером расхождения, что и до фикса; восстановление фикса —
обратно PASS. Проделано дважды (для standalone-скрипта и отдельно для
новых vitest-тестов).

**Новые постоянные артефакты:**
- `backtest/htf-resample-stability-audit.ts` (`npm run
  backtest:htf-resample-audit`) — standalone-скрипт по методике
  `backtest/harmonic-audit.ts`, PASS/FAIL с ненулевым exit-кодом.
- `order-block-strategies.test.ts` / `fvg-strategies.test.ts`: новый
  `describe`-блок в каждом файле с тем же сценарием как обычный vitest-тест
  (запускается в `npm run test`).

## Рекомендация 2: асимметричные AB/BC-фикстуры с численной проверкой PRZ

**Диагноз.** Существующие 14 тестов `harmonic-pattern.test.ts` не поймали
ранее найденный и исправленный баг "PRZ для ab-cd считался от BC вместо
AB" (см. `docs/audit/2026-09-harmonic-module-synthetic-audit.md`, раздел
2), поскольку их фикстуры имели AB и BC достаточно близкими по величине,
чтобы разница между базами теряться в допуске `fibTolerancePct`.

**Добавлено.** Пять новых тестов (по одному на каждый из 5 типов
паттерна — Gartley/Bat/Crab/Butterfly/AB=CD) с BC, отличающимся от AB
более чем в 2 раза (`bc_ab` у обеих границ допустимого диапазона [0.382,
0.886] — ~0.40 и ~0.85, встречаются в разных фикстурах), с явной
численной проверкой `przLow`/`przHigh` (`toBeCloseTo`, а не просто
"PRZ существует"). Значения для проверки взяты не "на бумаге" по формуле,
а как фактический вывод реального `detectHarmonicPattern()` на этих
фикстурах (ZigZag сам находит pivot-точки по ATR-порогу, поэтому
итоговые X/A/B/C/D не обязаны совпадать день-в-день с "идеальными"
точками, заданными через `targets`) — так тест остаётся регрессионным
(ловит будущие изменения формулы), а не проверкой соответствия
вручную посчитанным ожиданиям.

**Проверено, что тест ловит именно тот класс бага, для которого он
написан:** временно вернул старую (ошибочную) базу `cdProjectionBase =
bc` вместо `ab` в ветке `ab-cd` (`harmonic-pattern.ts`) — новый тест
`AB=CD: bc_ab ≈ 0.40 ...` действительно упал (`przLow`/`przHigh`
разошлись на ~30 пунктов цены, `150.15` вместо ожидаемых `180.15`);
восстановление фикса — тест снова зелёный.

## Рекомендация 4: пересмотрено, изменений не потребовалось

`checkPrzConfluence()` в `harmonic-pattern.ts` уже содержит эпсилон
(`PRZ_EPS`) для вырожденного (нулевой ширины) PRZ ab-cd — сделано в
рамках предыдущего аудита, не трогалось.

Дополнительно пересмотрены аналогичные "точка/зона входит в диапазон"
проверки в `order-block-nested.ts`/`fvg-nested.ts`
(`overlapTop <= overlapBottom`) — это НЕ тот же класс вырождения: там обе
зоны (HTF и M1) имеют реальную ширину по построению, вырожденный
(нулевой ширины) диапазон математически не является неотъемлемым
свойством паттерна, как для ab-cd PRZ (`cdRange=[1,1]`). Оставлено как
есть — добавление эпсилона здесь изменило бы поведение (расширило бы
условие "перекрытие есть") без эмпирически подтверждённой необходимости;
если в будущем появятся конкретные наблюдения на реальных данных о
ложных `overlapTop <= overlapBottom` из-за округления при HTF-группировке
— стоит вернуться к этому пункту отдельно, с тем же эмпирическим
подходом, что и Рекомендация 1/3 выше.

## Рекомендация 6: задокументировано ограничение бэктеста

`README.md` дополнен разделом "Бэктест: что на самом деле измеряют
метрики" — явная оговорка, что `resolveOutcome()`/`applySpreadToOutcome()`
резолвят исход следующей свечой после входа (не фактическим касанием
SL/TP), поэтому текущие R-метрики бэктеста измеряют точность
краткосрочного предсказания направления, а не качество структурных
уровней SL/TP конкретного детектора.

## Что НЕ было сделано в этой сессии (осознанно, не по недосмотру)

- Elliott Wave / Wyckoff (упомянуты в Рекомендации 3 как кандидаты для
  той же методики) — не тронуты: рекомендация явно говорит "не чинить
  вслепую по аналогии", а эмпирическая проверка именно этих двух
  модулей — отдельная по объёму задача, не помещающаяся в эту сессию.
- Отдельный режим резолвинга исхода бэктеста по первому касанию TP/SL
  (альтернатива направлению следующей свечи, упомянуто в Рекомендации 6)
  — согласно самому документу, это отдельная, более крупная задача
  (`backtest/simulator.ts`/`src/decision/outcome-scheduler.ts`,
  потенциально сам демо-счёт), требующая отдельного явного решения, а не
  тихого предположения. Пока только явно задокументировано ограничение.

## Проверки

Окружение без доступа к сети — `npm install` невозможен
(`npm error 403 ... registry.npmjs.org`), `node_modules` отсутствует, из-за
чего недоступны `npm run test`/`npm run lint`/`npm run typecheck` в
исходном виде (та же ситуация, что и в
`docs/changelog/CHANGES_APPLIED_PREVIOUS.md`). Вместо этого:

- Все изменённые/новые функции (`resampleCandles`, `findHarmonicZigZagPoints`,
  `detectHtfObZones`, `detectHtfFvgZones`, `detectHarmonicPattern`)
  выполнены напрямую через `tsx --tsconfig backtest/tsconfig.json`
  (тот же движок, что и `npm run backtest*`) — реальный TypeScript,
  реальная логика, без моков.
- `backtest/htf-resample-stability-audit.ts` — запускается, PASS для обоих
  детекторов (`npm run backtest:htf-resample-audit`, добавлен в
  `package.json`).
- Пять новых тестов `harmonic-pattern.test.ts` — вручную воспроизведены
  через `tsx`-скрипт с той же логикой сравнения, что и `expect(...)
  .toBeCloseTo(...)` (та же формула допуска `0.5 × 10^-precision`) — все
  24 индивидуальные проверки (5 фикстур × ~5 assertions) зелёные.
- Оба новых `describe`-блока в `order-block-strategies.test.ts` /
  `fvg-strategies.test.ts` — логика идентична уже проверенному
  standalone-скрипту, отдельно перепрогнана через `tsx` перед вставкой в
  тестовый файл.
- Методология каждой новой проверки валидирована в обе стороны (временный
  откат фикса → тест/скрипт корректно красный → восстановление фикса →
  снова зелёный) — описано в соответствующих разделах выше.
- Полноценный `npx tsc --noEmit -p tsconfig.app.json` по всему проекту НЕ
  запускался (нет `node_modules`, включая типы `@sentry/react`,
  `zustand`, `zod` и т.д. — попытка дала бы шум несвязанных с этой правкой
  ошибок разрешения модулей). Изменения точечно устного/построчного
  ревью на соответствие уже принятым в проекте паттернам (сигнатуры,
  именование, стиль комментариев "BUGFIX (аудит ...)").
- `npm run lint`/`npm run build`/`npm run e2e` не запускались — та же
  причина (нет сети/`node_modules`). Рекомендуется прогнать
  `npm run ci && npm run build` в CI/локальном окружении с доступом к
  сети перед мержем — как и для предыдущих сессий без доступа к сети.
