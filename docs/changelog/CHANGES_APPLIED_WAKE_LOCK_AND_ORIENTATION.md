# CHANGES_APPLIED_WAKE_LOCK_AND_ORIENTATION.md

Дата: 2026-08-29.

Промт: «1) Можно ли сделать возможным, чтобы приложение работало и в
спящем режиме телефона/компьютера и демо-счёт продолжал открывать
сделки. 2) Сделай возможным, чтобы приложение переворачивалось при
смене положения экрана телефона.»

## Задача 2 — Переворот экрана

**Аудит.** `useLandscape.ts` / `LandscapeControls.tsx` / `App.tsx` уже
умели адаптировать раскладку под landscape/portrait — это работало в
обычной вкладке браузера. Проблема была не в React-коде, а в
`vite.config.ts`: манифест PWA задавал `orientation: 'portrait'`. В
установленном на телефон приложении (`display: 'standalone'`)
Android/Chromium применяет это поле как жёсткий системный лок
ориентации и просто не пропускает событие поворота в JS/CSS вообще —
никакая клиентская адаптация до него не долетала.

**Файл:** `vite.config.ts`.
**Изменение:** `orientation: 'portrait'` → `orientation: 'any'`.
Проверено сборкой — `dist/manifest.webmanifest` содержит
`"orientation":"any"`.

## Задача 1 — Работа в «спящем режиме»

**Важное техническое ограничение (сообщено пользователю в чате).**
Гарантированное продолжение работы JS (и, соответственно, открытия
демо-сделок) при заблокированном/выключенном экране устройства
невозможно ни для одного сайта или PWA без нативного
background-сервиса — это ограничение платформы (iOS Safari
замораживает вкладку через секунды в фоне; Android глушит таймеры и
рвёт WebSocket через пару минут в фоне), а не текущей архитектуры.
Вся торговая логика в этом приложении (генерация сигналов,
открытие/закрытие демо-сделок) выполняется на клиенте по тикам из
WebSocket — при заморозке вкладки она физически не может продолжать
работу. Единственный технически честный способ снять эту зависимость
от сна устройства — перенести движок демо-сделок на сервер (Supabase
Edge Function по расписанию/pg_cron); это отдельная архитектурная
задача, не входящая в этот патч.

**Что сделано на клиенте (реально работает и покрыто typecheck/lint/
тестами).**

1. **`src/hooks/useWakeLock.ts`** (новый файл). Обёртка над Screen
   Wake Lock API: пока `enabled === true`, удерживает экран включённым
   (не даёт погаснуть по таймауту бездействия — самая частая причина
   обрыва сессии на практике). При потере видимости вкладки лок
   снимается браузером автоматически; хук сам переустанавливает его
   при возврате на вкладку (`visibilitychange`). Отсутствие поддержки
   API или отказ в получении лока — не критичная ошибка, приложение
   продолжает работать как раньше.

2. **`src/stores/settingsStore.ts`**. Добавлено персистентное поле
   `keepScreenAwake: boolean` (по умолчанию `true`) с сеттером
   `setKeepScreenAwake` — включено в `partialize`, версия схемы
   (`version: 12`) не менялась, так как это новое поле с дефолтом, не
   требующее миграции существующих данных (`persist` подставит
   дефолт для всех, у кого его ещё нет в localStorage).

3. **`src/App.tsx`**. Хук `useWakeLock` подключён с условием
   `phase === 'terminal' && keepScreenAwake && autoTradeEnabled`
   (`autoTradeEnabled` — из `useDemoAccountStore`) — экран удерживается
   только пока пользователь реально смотрит на работающий терминал с
   активной автоторговлей, а не всегда.

4. **`src/ui/SettingsPanel.tsx`**. Добавлен переключатель «Не
   выключать экран во время автоторговли» рядом с «Автооткрытие
   сделок», с пояснительным текстом прямо в UI о том, что полная
   работа при заблокированном экране устройства не поддерживается ни
   одним браузером.

**Сознательно не тронуто.** Существующий watchdog в
`connection-manager.ts` (проверка раз в 15 c, реконнект после 45 c
без тика) уже сам восстанавливает соединение после возврата вкладки в
фокус — трогать его логику (например, форсировать резинк на каждый
`visibilitychange`) не стали, чтобы не добавлять риск регрессии
(лишние полные переподключения/перезагрузку истории при обычном
быстром переключении вкладок) без чёткой пользы.

## Дополнение: перенос патча в ветку с фиксом «История сигналов»

Этот патч (Wake Lock + orientation) изначально был сделан поверх другой
ветки, не содержавшей фикс синхронизации «История сигналов» с демо-счётом
(SignalCard.tsx / SignalFeed.tsx / PredictionAccuracyBadge.tsx /
tick-store/outcomes.ts). Перенесён вручную, файл за файлом
(vite.config.ts, src/hooks/useWakeLock.ts, src/App.tsx,
src/stores/settingsStore.ts, src/ui/SettingsPanel.tsx) — конфликтов не
было, зоны изменений не пересекались.

При переносе, а также при аудите принимающей ветки, обнаружены и
исправлены три независимых от wake-lock/orientation дефекта, уже
присутствовавшие в ней до переноса:

1. **`src/stores/useAnalyticsStore.ts`** — комментарий к `recomputeStats`
   утверждал (в настоящем времени), что непроторгованные сигналы
   помечаются бейджем «Не торговался» в `SignalCard.tsx`. Это устарело:
   ветка убрала эту отрисовку из `SignalCard.tsx` полностью (фильтрация
   теперь целиком на уровне `SignalFeed.tsx`). Комментарий поправлен.

2. **Отсутствовала зависимость `@testing-library/jest-dom`.** Новые тесты
   `SignalFeed.test.tsx` и `PredictionAccuracyBadge.test.tsx` используют
   матчер `toBeInTheDocument()`, но пакет не был установлен и не
   подключён в `src/test/setup.ts` — `npm run typecheck` не проходил.
   Добавлена зависимость (`^6.9.1`) и `import
   '@testing-library/jest-dom/vitest'` в setup.

3. **Два падающих теста** (воспроизводились и в исходной, немодифицированной
   ветке — не регрессия от переноса):
   - `outcomes.test.ts` — фейковая модель калибровки (`{}`) не реализовывала
     `getSampleCount()`, который реально вызывается в
     `tick-store/outcomes.ts` при логировании; добавлена заглушка
     `getSampleCount: () => 0`.
   - `SignalFeed.test.tsx` — тест ошибочно предполагал, что полноразмерная
     (не-compact) карточка активного сигнала показывает текст «Прибыль»/
     «Убыток». На деле не-compact `SignalCard` никогда не отображал
     `OutcomeBadge` (это поведение не менялось этим патчем) — тест
     переписан на фактическое поведение: активная карточка не показывает
     исход, а «Прибыль» не должна встречаться нигде (не дублируется и в
     истории, откуда сигнал исключён по id).

Также стоит отметить: у самого фикса «История сигналов» (SignalCard/
SignalFeed/PredictionAccuracyBadge/outcomes.ts) нет отдельного
CHANGES_APPLIED_*.md, в отличие от остальных патчей в этом репозитории —
стоит завести его отдельно для полноты истории изменений.
