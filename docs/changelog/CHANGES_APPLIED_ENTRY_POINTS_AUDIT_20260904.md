# Аудит по докам «Анализ приложения» / «Что для этого нужно» / «Проверь» / «Реальные проблемы» — 2026-09-04

Задача: сверить фактическую реализацию фичи «точки входа на графике +
структурированная атрибуция причин сигнала (индикаторы/паттерны/стратегии) +
постмортем-экспорт по убыточным/любым сделкам» с требованиями из
приложенных документов, устранить найденные расхождения и реализовать три
явно запрошенных доработки. Все 6 проблем, перечисленных в «Реальные
проблемы», подтверждены построчным чтением кода (не с чужих слов) и
устранены.

## 1. Свеча входа выпадала из `chartContext` (Реальные проблемы, п.1)

`src/decision/signal-builder.ts`: `candlesBefore` строился срезом
`candles.slice(..., candles.length - 1)` — с ИСКЛЮЧЁННЫМ последним
индексом, то есть без самой свечи `lastCandle` (её `time` идёт в
`signal.time`). Одновременно `candlesAfter`
(`src/decision/outcome-scheduler.ts`, `getCandlesAfterSignal`) берёт только
строго `c.time > signal.time`. В сумме свеча входа не попадала НИ В ОДИН
из двух массивов — а именно она нужнее всего для визуальной
реконструкции точки входа (замена ручного скриншота, см. «Что для этого
нужно», Раздел 2).

Фикс: срез теперь заканчивается на `candles.length` (включительно) — свеча
входа становится последним элементом `candlesBefore`.

## 2. SL/TP/expiry отсутствовали в постмортем-отчёте (Реальные проблемы, п.2)

`src/lib/trade-report.ts`: `buildPostMortemReport()` выводил entryPrice,
score и calibratedProbability, но не stopLoss/takeProfit/recommendedExpiry
— хотя «Что для этого нужно», Раздел 1, явно перечисляет их как
необходимые для вывода вида «сетап был верный, но SL слишком тесный».
Добавлены в строку «Вход». Заодно вынесено дублировавшееся форматирование
экспирации (`formatExpiry` было отдельно и идентично в `SignalCard.tsx`) в
общий `formatDurationShort()` (`src/lib/utils.ts`).

## 3. Секция факторной аналитики в CalibrationPanel (Реальные проблемы, п.3)

`factors[]` (структурированная атрибуция: индикатор/паттерн/стратегия +
вклад + аргумент) копился в каждом сигнале и уходил в БД, но нигде в UI не
было сводки «какой фактор как часто встречается и какой у него винрейт» —
только вручную, по одному сигналу через экспорт. Добавлены:

- `src/ui/factor-analytics.ts` — `computeFactorStats()`: группировка
  резолвнутых (`outcome !== 'pending'`, `tradeOpened !== false`) сигналов по
  `factors[].name`, с `sampleCount`/`decidedCount`/`winRate` и порогом
  `MIN_FACTOR_SAMPLES = 5` для пометки «мало данных» (тот же принцип
  надёжности выборки, что уже был в `calibration-buckets.ts`).
- Новая секция «АНАЛИТИКА ПО ФАКТОРАМ» в `CalibrationPanel.tsx` —
  таблица «Фактор / N / Винрейт», отсортированная по количеству сделок.

## 4. Дублирование `handleExport()` (побочно найдено при работе над п.2)

`SignalCard.tsx` и `EntryPointPopup.tsx` содержали один-в-один
скопированную функцию экспорта отчёта (копирование в буфер + скачивание
.md). Вынесено в `src/hooks/useTradeReportExport.ts` — единственный
источник истины, оба компонента теперь используют хук.

## 5. Автоудаление истории раз в сутки (Реальные проблемы, п.6)

Ранее это было не просто «не сделано», а прямо законтрено:
`useAnalyticsStore.ts` содержал комментарий «должен очищаться только
вручную», `SignalFeed.tsx` вызывал удаление только по клику кнопки,
`supabase/functions/delete-all-signals/index.ts` — полный снос таблицы по
явному запросу клиента, без расписания.

Архитектура (клиентская проверка vs pg_cron) и обоснование выбора подробно
описаны прямо в коде — см. JSDoc `src/hooks/useAutoCleanupSignals.ts`.
Коротко: выбран клиентский вариант, т.к. это client-only SPA без
собственного сервера (деплой на bolt.new), история — уже единый глобальный
канонический ресурс с единственным путём полной очистки
(`deleteAllSignals()`), и часть инсталляций вообще работает без Supabase
(fallback в `localStorage`), куда `pg_cron` в принципе не дотянется.

Реализация:
- `useAnalyticsStore.maybeRunAutoCleanup()` — чистая функция состояния:
  при самом первом запуске только фиксирует точку отсчёта (не удаляет
  накопленную историю сразу после обновления приложения), далее — очищает
  раз в `AUTO_CLEANUP_INTERVAL_MS` (24ч).
- `useAutoCleanupSignals()` — хук-оркестратор побочных эффектов
  (`clearOutcomeScheduler()` + `deleteAllSignals()`), подключён в
  `App.tsx` на верхнем уровне; проверка — на монтировании и раз в час,
  пока вкладка открыта (для долгих непрерывных сессий, см.
  `useWakeLock.ts`).
- `lastAutoCleanupAt` добавлен в `partialize` стора, чтобы точка отсчёта
  переживала перезагрузку страницы.
