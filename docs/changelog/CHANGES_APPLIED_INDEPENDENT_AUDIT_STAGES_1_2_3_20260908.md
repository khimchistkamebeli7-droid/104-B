## Находка 1 — `winRate` в сторе делят ATR-бэктест и живая статистика

`useAnalyticsStore.ts` уже один раз чинил ровно этот класс бага для
`calibrationSampleCount`/`calibrationReady` (см.
`CHANGES_APPLIED_CALIBRATION_PER_SYMBOL_STAGE1_20260906.md`, Этап 1 аудита
п.3: три источника — ATR-бэктест / ML-семпл-каунт / просто счётчик
резолвнутых сигналов — писали в одно общее поле с разными порогами
готовности) — и завёл под это три честно названных поля
(`mlSampleCount`/`mlReady`, `atrBacktestTrades`, `liveCompletedCount`).

Поле `winRate` осталось не разведено. `recomputeStats()` пишет туда живой
винрейт по реально проторгованным резолвнутым сигналам — сам код
документирует это как производную величину (`partialize`: "calibration*/
winRate — производные величины, пересчитываемые из signals"), и
`StatusBar.tsx`/`CalibrationPanel.tsx` ("Винрейт (лайв)") оба читают его
именно с этим ожиданием. Но `setCalibrationResult()` (запускается кнопкой
"Калибровать" в блоке ATR-бэктеста — historical backtest подбора
множителя стопа/цели, полностью отдельная фича) тоже писал в `winRate`
свой результат — `result.winRate` из симуляции на истории, а не с реальных
демо-сделок.

Эффект: после запуска ATR-бэктеста лейбл "Винрейт (лайв)" в панели
калибровки и цифра винрейта в `StatusBar` временно показывали
исторический результат бэктеста вместо реального живого винрейта — до
следующего резолвнутого сигнала, который вызывает `recomputeStats()`
заново и перезаписывает `winRate` обратно.

**Фикс**: `winRate` в `setCalibrationResult()` больше не трогается.
Результат ATR-бэктеста для этого поля пишется в новое отдельное поле
`atrBacktestWinRate` (тот же принцип, что уже применён к
`atrBacktestTrades`). Сам ATR-блок в `CalibrationPanel.tsx` не менялся —
он и раньше показывал `result.winRate` напрямую из объекта результата, а
не из общего поля стора, так что видимого регресса в самом ATR-блоке не
было — расходился только "живой" лейбл в двух других местах.

Файлы: `src/stores/useAnalyticsStore.ts`
(`AnalyticsState.atrBacktestWinRate`, `setCalibrationResult`, `clearAll`),
`src/stores/useAnalyticsStore.test.ts` (обновлены/добавлены тесты
`describe('setCalibrationResult')`, проверяющие, что `winRate` не
трогается).

## Находка 2 — предпросмотр надёжности паттернов не сбрасывается при смене инструмента

`CalibrationPanel.tsx` уже реализует per-symbol изоляцию для калибровки
надёжности паттернов (см.
`CHANGES_APPLIED_CALIBRATION_STAGE2_5_REVIEW_CLEANUP_20260908.md`) —
`applyReliabilityMultiplierUpdatesForSymbol(symbolId, ...)` пишет только
для текущего инструмента. Но состояние `reliabilityPreview` (то, что
показывает таблицу "было/станет" после нажатия "Калибровать" в блоке
"КАЛИБРОВКА НАДЁЖНОСТИ ПАТТЕРНОВ") — обычный `useState`, не привязанный к
`symbolId`, и не сбрасывался при смене инструмента.

Сценарий: пользователь на BTCUSDT нажимает "Калибровать" → видит
предпросмотр, посчитанный по факторной статистике BTCUSDT → переключает
инструмент на EURUSD, не нажав "Отмена" → пояснительный текст под таблицей
("применяется только к {symbol.displayName}") уже показывает "EURUSD",
таблица всё ещё показывает старые числа BTCUSDT → нажимает "Применить" →
`applyReliabilityMultiplierUpdatesForSymbol('EURUSD', <множители,
посчитанные по BTCUSDT>)`. Множители одного инструмента записываются как
override другого — ровно тот баг, для защиты от которого и вводился
per-symbol API в Этапе 2, просто через дыру, оставшуюся в UI-состоянии
компонента, а не в самом API.

**Фикс**: `useEffect(() => { setReliabilityPreview(null);
setReliabilityApplied(false); }, [symbolId])` — предпросмотр и баннер
"Применено" закрываются при любой смене активного инструмента; пользователю
нужно нажать "Калибровать" заново на новом инструменте, чтобы увидеть
предпросмотр именно по его данным.

Файлы: `src/ui/CalibrationPanel.tsx`, новый тест
`src/ui/CalibrationPanel.test.tsx`.

## Что не менялось

Все 27 пунктов приложенного отчёта независимого аудита (Раздел 1 — Этап 1,
9 пунктов; Раздел 2 — Этап 2, 9 пунктов; Раздел 3 — Этап 3, 4 пункта)
перепроверены построчно и подтверждены как реализованные согласно плану:
per-symbol карта калибровочных моделей, symbol-aware localStorage/Bolt
Database ключи, миграция `calibration_state` (singleton → per-symbol PK,
включая последующую hygiene-миграцию для `id`), разделение
`mlSampleCount`/`mlReady`/`atrBacktestTrades`/`liveCompletedCount`,
исключение timeout из обучающей выборки, явный `calibrationModel`-аргумент
в `recordOutcome`, per-signal routing по `symbolId` в
`tick-store/outcomes.ts`, формула `clamp(winRate / 0.5, 0.1, 1.5)`, все
четыре исключения в `pattern-reliability-calibration.ts`, дедупликация
факторов в `factor-analytics.ts`, per-symbol reliability override API в
`pattern-categories.ts`, проброс `symbolId` до `getReliabilityMultiplier`,
preview/apply/cancel/reset flow, удаление глобальных мутаторов с
сохранением legacy-ключа, `FEATURE_KEYS`/`FEATURE_COUNT` = 12,
`pattern_conf` как единственный скаляр для паттернов, независимость от
восьмикомпонентной `featureCalibration.ts`. Ни одна из уже пройденных
проверок повторно не переписывалась — изменения этого прохода
ограничены двумя находками выше.

Этап 3 (one-hot/multi-hot per-pattern feature vector) по плану сознательно
отложен до накопления 100+ исходов на инструмент через Этап 1 — трогать
его в этом проходе не требовалось и не предполагалось планом.
