Контекст (важно для роли команды экспертов)
Роль: старший React/TS-разработчик + архитектор + перф-инженер + QA-лид + безопасность/DevOps + мультидисциплинарная торговая аналитика (Price Action, SMC/ICT, Wyckoff, Elliott Wave, TA-индикаторы, Фибо/гармоники, волатильность, структурный анализ HH/HL/LL/LH, интермаркет, ICT Kill Zones, стратег).
С точки зрения торговой методологии (SMC/ICT) все 4 находки — не стилистика, а нарушение самой сути сетапа «Order Block Continuation»:
Правки №1 и №2 напрямую бьют по критерию свежести/непротестированности блока — ключевому качественному фильтру ICT-континуации (чем свежее непротестированный OB, тем выше вероятность отработки, т.к. рынок ещё не успел «съесть» его встречным потоком).
Правка №3 — про управление риском: тейк-профит должен идти по следующему структурному уровню ликвидности (OB/FVG/S-R), а не по произвольному ATR×2, который игнорирует реальную структуру рынка.
Правка №4 — техническая рассинхронизация индексов, влияющая на точность фильтра momentum-экстремума.
🔴 Правка №1 (приоритет 1, системная — 3 стратегии, лёгкое решение уже есть в проекте)
Файлы и текущие строки:
order-block-continuation.ts:42-45
strong-order-block-reaction.ts:53-55
macd-deceleration-continuation.ts:302-304
super-order-block.ts:40-49, 118, 121
Проблема (подтверждена в коде): все три стратегии зовут superOrderBlocks(candles, 100, { structure, requireStructureConfluence: true /* или structure !== undefined */ }). Внутри super-order-block.ts hasStructureConfluence считается через structureConfluence(options?.structure, direction) — это сверка направления блока с текущим снапшотом structure.trend/bos/choch (см. computeStructure() в trend-structure.ts, которая всегда возвращает bos/choch только для последней свечи, а не историю). Сам файл super-order-block.ts содержит явный комментарий-предупреждение об этом (строки 40-49): гейтинг по этому флагу «сделает функцию возвращающей почти ничего почти всегда», потому что bos/choch edge-triggered и сверяются не с моментом формирования блока, а с «сейчас».
Хорошая новость — решение почти бесплатное: в проекте уже есть корректная реализация в smart-money.ts (calcSmartMoney() → SmartMoneyOrderBlock.hasStructureConfluence, вычисляется через hasStructureConfirmation(breakIndex, direction) — поиск BOS в окне structureConfirmWindow (по умолчанию 20) баров после формирования блока, requireStructureConfluence по умолчанию true). И этот результат уже считается один раз в full-snapshot.ts:43 (calcSmartMoney(candles)) и прокидывается как ctx.smartMoney во все паттерн-детекторы через detectAllPatterns() (src/compute/patterns/index.ts). Более того:
detectStrongOrderBlockReaction уже принимает smartMoney?: SmartMoneyResult пятым параметром (strong-order-block-reaction.ts:37), но не использует его — внутри всё ещё вызывается superOrderBlocks() с багованным гейтом.
detectOrderBlockContinuation и detectMacdDecelerationContinuation вообще не получают smartMoney — их сигнатуры и точки вызова в patterns/index.ts:252-253 нужно расширить.
Что сделать:
В patterns/index.ts изменить вызовы (строки 252-253) — прокинуть ctx.smartMoney в detectOrderBlockContinuation и detectMacdDecelerationContinuation, как уже сделано для detectStrongOrderBlockReaction (строка 251).
В каждом из трёх файлов стратегий заменить superOrderBlocks(candles, 100, { structure, requireStructureConfluence: true }) на использование уже переданного smartMoney.orderBlocks, отфильтрованного по направлению и статусу (как сейчас фильтруются блоки от superOrderBlocks).
Важно про схему данных — SmartMoneyOrderBlock не идентичен SuperOrderBlock: поля top/bottom вместо high/low, type вместо direction, и нет поля index (только time). Для строк, где нужен blockIdx (правка №2 в order-block-continuation.ts завязана на позицию блока в массиве candles), построить один раз Map&lt;time, index&gt; по candles (O(n) один проход) и делать по нему O(1)-лукап вместо candles.findIndex() на каждый блок — на M1-потоке с частым пересчётом это важно для перформанса.
Поле status (OrderBlockStatus) идентично в обеих схемах — фильтры b.status === 'untested' || b.status === 'tested-hold' (OBC) и b.status !== 'broken' (strong-order-block-reaction) переносятся без изменений.
В macd-deceleration-continuation.ts:302-304 (там это мягкий бонус +0.15, не жёсткий гейт) — та же замена: smartMoney.orderBlocks вместо superOrderBlocks(..., requireStructureConfluence: true).
После замены отдельно проверить: не остались ли в super-order-block.ts другие живые вызовы с requireStructureConfluence: true — если нет, оставить флаг как есть (он предупреждён в доке и по умолчанию false), не нужно менять сам super-order-block.ts.

obHistIdxизмеряется как фиксированное смещение blockIdx - windowStart в позиционном пространстве исходного (несжатого) окна , но применяется к windowAbs— массиву, из которого уже есть вырез null-значения (MACD в разгоне/на старте истории). Если бы один бар в окне до блока индекса имел histogram === null, все остальные индексы windowAbsбыли бы сдвигом на 1 соответственно исходных позиций, и obHistIdxначало не имело бы значения MACD-гистограммы самого блока , а на соседнем баре. При получении прогретых данных (около candles.length &lt; 40-50, около периода macdSlow=26 + сигнальная 9) это может реально измениться. Практический эффект сейчас невелик (окно и так короткое — см. п.2 — и на «горячих» данных nullтам маловероятен), но при доработке п.2 (расширении/переработке окна) эта проблема становится заметнее, поэтому стоит исправлять постоянно.
Рекомендация: положить индексный блок в исходном (несжатом) массиве и добавить значение до фильтра null, либо сохранить пару (index, value)вместо плоского number[], чтобы избежать рассинхронизации.

Как это соотносится с общепринятой методологией (для сверки)
Продолжение блока заказов ICT : вход по продолжению тренда от свежего, непротестированного ордер-блока — стандартный, хорошо задокументированный сетап; критично важна именно аккуратность (чем свежее непротестированный блок, тем выше качество входа, так как ещё не было возможности его «есть» встречным потоком) — и именно аккуратность ломает баг из этого п.2, отсекая самый свежий (1-баровый) случай в первую очередь.
Управление риском (SMC/ICT) : тейк-профит по следующему структурному принципу ликвидности — то же общепринятое правило, которое упоминалось в отчёте по «Реакции на снятие ликвидности» (п.6 там). Здесь код для этого уже написан ( findTargetZone), но не подключен — см. п.3.

===== system =====
Торговая система «Продолжение от ордер-блока» (Order Block Continuation, OBC)
Проект: project-bolt-github-ttgyevpp · Рынок: Forex, валютные пары · Таймфрейм: M1 Статус: система описана по реальному коду (order-block-continuation.ts, super-order-block.ts, smart-money.ts, signal-builder.ts, trade-levels.ts) — с учётом 4 правок, согласованных ранее (структурное подтверждение по времени формирования блока, окно свежести, использование targetZone, синхронизация индекса MACD). Без этих правок пп. 3.1–3.3 работают некорректно — см. раздел 6.
1. Философия сетапа
OBC — это ICT-сетап продолжения тренда от свежего непротестированного Order Block: цена импульсно уходит от блока, оставляя институциональный след (displacement), и стратегия ловит момент, пока блок ещё «чист» — рынок не успел его отработать встречным потоком. Ключевая переменная качества — свежесть: чем меньше баров прошло с формирования блока, тем выше вероятность отработки. Это не разворотный сетап (в отличие от liquidity-sweep-reaction) и не пробойный (в отличие от impulse-breakout) — OBC торгует по направлению уже начавшегося движения, используя OB как точку опоры для входа, а не как зону возврата цены.
В общей архитектуре приложения OBC — один из 8 сигнальных источников, взвешенно суммируемых в signal-builder.ts в единый Signal (бонус +0.55 × confidence, второй по величине вес).

3. Формальные правила системы
3.1 Обнаружение валидного Order Block
Геометрия: bullish OB — свеча с close &lt; open, следующая свеча закрывается выше её high; bearish — зеркально.
Displacement-фильтр: диапазон импульсной свечи ≥ minDisplacementAtrMultiple × ATR (по умолчанию задаётся в super-order-block.ts/smart-money.ts) — отсекает случайные, «неинституциональные» пробои.
Структурное подтверждение (после правки №1): BOS/CHoCH в том же направлении в окне structureConfirmWindow (по умолчанию 20) баров после формирования блока — не против текущего снапшота структуры. Источник — smartMoney.orderBlocks (hasStructureConfluence), уже посчитанный один раз в full-snapshot.ts и переданный в контексте.
Свежесть (после правки №2): 1–3 бара с момента формирования (MAX_FRESH_CANDLES = 3), окно ретроспективное — не обрезает 1-баровые блоки.
Статус зоны: untested или tested-hold (не broken) — блок ещё не пробит close-баром в обратную сторону.
3.2 Триггер сигнала (momentum-подтверждение)
MACD-экстремум (после правок №2 и №4): |MACD histogram| бара формирования блока — в пределах 80% от максимума в ретроспективном окне N_BARS = 12 баров до блока, индекс без рассинхронизации при null-значениях гистограммы.
RSI hard-фильтр: сделка отклоняется, если направление buy при RSI &gt; 75 или sell при RSI &lt; 25 — не входить по тренду на уже глубокой перекупленности/перепроданности.
EMA-confluence бонус: блок лежит на «дальней» стороне быстрой EMA относительно направления (bullish блок выше emaFast, bearish — ниже).
BB-expansion бонус: ширина полос Боллинджера &gt; 2×ATR (аппроксимация расширения волатильности).
Session Kill Zone бонус: торговля активна во время London/New York/Overlap (isHighLiquiditySession).

3.4 Вход, стоп, тейк, экспирация
Вход: маркет-ордер по цене закрытия последней свечи + половина спреда в сторону сделки (tradeEntryPrice).
Stop Loss: entry ± ATR × atrMultiplier (общий для большинства стратегий механизм; структурный стоп по OB-границе для OBC пока не реализован — см. §6 как рекомендацию).
Take Profit (после правки №3): ближайший структурный уровень (targetZone — активная OB-зона / непробитый FVG / S-R в направлении сделки), если это даёт RR ≥ 1.5; иначе — откат на entry ± ATR × atrMultiplier × 2.
Экспирация: 1–3 бара M1, размер зависит от волатильности (recommendedExpiry: ATR/entryPrice &lt; 0.5% → 3 бара, &lt; 1% → 2 бара, иначе 1 бар).
Вклад в композитный Signal: +0.55 × confidence — второй по весу бонус среди 8 стратегий-источников.
3.5 Инвалидация
OB инвалидируется по закрытию свечи за противоположную границу зоны (не по хвосту/wick) — сохраняет консистентность с остальными SMC-модулями приложения (analyzeOBTouches).
Сделка резолвится через outcome-scheduler.ts: TP / SL / истечение экспирации — что наступит раньше.
4. Ручной дискреционный чек-лист (не автоматизировано в приложении)
Использовать как дополнительный фильтр поверх сигнала приложения, если трейдер лично отслеживает эти данные на графике — приложение их не считает:
Wyckoff (фазовый): сделка не должна открываться в явной противоположной фазе распределения/накопления (Spring/Upthrust) на старшем таймфрейме — точечный VSA-бар (vsa-classifier.ts) это не заменяет, у него только однобарный, низковесовой сигнал.
Elliott Wave: избегать входа по продолжению против явно затухающей 5-й волны или в конце коррекционной ABC-структуры того же направления, куда указывает OBC.
Фибо/гармоники: дополнительное усиление сигнала, если OB совпадает с уровнем 0.618/0.786 коррекции последнего значимого импульса, либо с точкой завершения гармонического паттерна (Gartley/Butterfly/AB=CD) того же направления.
Интермаркет: для сильно коррелирующих с DXY пар (EURUSD, GBPUSD, USDJPY) сверить, не идёт ли направление сделки против текущего движения индекса доллара на момент сигнала.

6. Что нужно доработать в коде, чтобы система была замкнута
1–4. Четыре правки аудита (structural confluence по времени формирования, окно свежести, использование targetZone для TP, синхронизация obHistIdx) — уже описаны в отдельном промте исправления, здесь не дублируются.
Опциональные усиления сверх аудита (не обязательны, но логично продолжают систему):
Структурный SL для OBC — стоп за противоположной границей OB-зоны вместо общего ATR-множителя, по аналогии с computeBreakoutTradeLevels/computeLiquiditySweepTradeLevels в trade-levels.ts.

Подключить vsa-classifier.ts как маленький confidence-бонус (модуль уже помечен как низковесовой by design — использовать соответственно).
